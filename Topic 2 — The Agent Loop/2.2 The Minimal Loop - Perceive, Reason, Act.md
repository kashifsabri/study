

A robot vacuum does three things, over and over:

1. **Feel:** the bumper says "something's in front of me."
2. **Think:** "okay, turn left."
3. **Move:** it turns left.

Then it feels again. Feel, think, move. Feel, think, move.

An agent is the same. It **looks** at what it knows, **thinks** about what to do next, and **does** it. Then it looks again.

---

## Simple technical version

Three verbs. That's the whole loop.

```
        ┌──────────────────────────────────────────┐
        ▼                                          │
   1. PERCEIVE                                     │
   build what the model will read                  │
   (task + history + tool results)                 │
        │                                          │
        ▼                                          │
   2. REASON                                       │
   call the model, get back a proposal             │
        │                                          │
   ┌────┴─────────────┐                            │
   ▼                  ▼                            │
 "answer"        "run this tool"                   │
   │                  │                            │
 STOP                 ▼                            │
                 3. ACT                            │
                 runtime checks and runs it        │
                      │                            │
                      ▼                            │
                 result saved in history ──────────┘
```

Who does each part:

|Part|Robot vacuum|Our agent|Who does the work|
|---|---|---|---|
|Perceive|Bumper sensor|Build the text the model will read|Our code|
|Reason|Tiny program picks a direction|Call the model, read its reply|The model|
|Act|Motors turn the wheels|Run the tool the model asked for|Our code|

Look at the last column. **The model only does the middle part.** Perceive and act are ours. The model never touches the world. It reads text and writes text.

### What "perceive" really means here

The model can't see anything. So "perceive" means: **our code decides what text to paste in front of the model this time.** That's it. What we leave out, the model never knows.

### What "reason" really returns

Not an action. A **proposal**. Either:

|Reply type|Meaning|What happens next|
|---|---|---|
|answer|"I'm done, here's the result"|Loop stops|
|tool request|"I'd like this tool run with these inputs"|Runtime decides whether to run it|

### What "act" really does

It doesn't just run the tool. It first checks: does this tool exist? Are the inputs valid? Is it allowed? Only then does it run. The result goes back into history as **data**.

## Code

A tiny agent that does math with two tools. The model is fake and follows a script, so you can run it for free.

```python
# ---------- tools ----------
def multiply(a, b): return a * b
def add(a, b):      return a + b

# WHY a dict: the runtime keeps the list of what is allowed.
# The model can only ASK for names on this list.
TOOLS = {"multiply": multiply, "add": add}


# ---------- 2. REASON (fake model) ----------
# A real model reads text and writes text. This fakes it with rules.
def reason(messages):
    tool_results = [m["content"] for m in messages if m["role"] == "tool"]

    if len(tool_results) == 0:
        return {"type": "tool", "tool": "multiply", "args": {"a": 12, "b": 7}}
    if len(tool_results) == 1:
        return {"type": "tool", "tool": "add",
                "args": {"a": int(tool_results[0]), "b": 5}}
    return {"type": "answer", "text": f"The result is {tool_results[-1]}"}


# ---------- 1. PERCEIVE ----------
def perceive(history):
    # WHY this is its own function even though it does almost nothing:
    # later this is where we choose WHAT the model sees. Cut old
    # messages, add memory, mark data as data. Keeping it separate
    # now means we don't have to untangle it later.
    return list(history)   # a copy, so the model call can't change our history


# ---------- 3. ACT ----------
def act(proposal):
    name = proposal["tool"]

    # WHY check before running: the model PROPOSED this.
    # It could ask for a tool that doesn't exist, or one we don't allow.
    if name not in TOOLS:
        # WHY we return the error as text and don't crash:
        # the model can read it and try something else. A bad
        # proposal is normal, not a disaster.
        return f"error: no tool called '{name}'"

    return str(TOOLS[name](**proposal["args"]))


# ---------- the loop ----------
def run(question, max_steps=6):
    history = [{"role": "user", "content": question}]

    for step in range(1, max_steps + 1):
        messages = perceive(history)
        proposal = reason(messages)

        # WHY print every step: this is our first trace.
        # If we can't read what the agent did, we can't fix it.
        print(f"step {step}: model proposed -> {proposal}")

        if proposal["type"] == "answer":
            return proposal["text"]

        # WHY save the proposal too, not just the result:
        # next turn the model must see what it asked for,
        # or it can't connect the result to the request.
        history.append({"role": "assistant", "content": str(proposal)})

        result = act(proposal)
        print(f"         runtime got   -> {result}")
        history.append({"role": "tool", "content": result})

    raise RuntimeError("ran out of steps")


print(run("What is 12 times 7, plus 5?"))
```

```
step 1: model proposed -> 
		{'type': 'tool', 'tool': 'multiply', 'args': {'a': 12, 'b': 7}}
         runtime got   -> 84
step 2: model proposed -> 
		{'type': 'tool', 'tool': 'add', 'args': {'a': 84, 'b': 5}}
         runtime got   -> 89
step 3: model proposed -> 
		{'type': 'answer', 'text': 'The result is 89'}
		
The result is 89
```


### Break it on purpose

Make the model ask for a tool that doesn't exist:

```python
# Change the first proposal inside reason() to:
return {"type": "tool", "tool": "delete_everything", "args": {}}
```

What you'll see: `act` refuses, returns `error: no tool called 'delete_everything'`, and that error goes back into history as data. Nothing was deleted, because the model asked and the runtime said no. That gap between asking and doing is the most important idea in this whole project.

## Real-life examples

### How Claude does it

Perceive: my input is built for me. It contains the system rules, our conversation, and any tool results so far. I never pick what goes in.

Reason: I read all of that and write a reply. If I want a search, I write a request for one. I don't run it.

Act: the system around me runs the search and pastes the results back into my input. Then I reason again.

I have no way to run anything on my own. I can only ask.

### How ChatGPT does it

Same three parts. When ChatGPT runs Python for you, the model writes the code (reason), a sandbox runs it (act), and the output is put back in front of the model (perceive on the next turn). If the code errors, the error is just more text for the next turn.

### In real products

|Product|Perceive|Reason|Act|
|---|---|---|---|
|Coding agent|Task + files read so far + test output|Model picks the next edit|Editor tool changes the file|
|Support agent|Ticket + order lookup result|Model decides refund or not|Refund API is called|
|Browser agent|Text of the current page|Model picks what to click|Browser clicks it|

## Where this lands in our build

1. **Each verb becomes its own piece.** Perceive becomes the context builder. Reason becomes the model provider. Act becomes the policy check plus the tool runner. Keep them as three separate functions from day one.
2. **Reason never calls a vendor directly.** In the code above, `reason` is fake. In the real build it calls a model provider interface, and Groq sits behind it. The loop never knows which vendor it is.
3. **The gap between reason and act is where the safety goes.** The check in `act` today is one `if`. Later it becomes validation, permission rules, and the place TinySeal plugs in.
4. **The printed steps are the seed of the trace.** Real version: every proposal and result written down, with time and cost.
5. **Target agent (still open).** Write down what its perceive step would contain and what its two or three tools are. If you can't, the agent isn't specific enough yet.

## Say it to your manager

> "The agent runs three steps in a circle: build what the model reads, ask the model what to do, then have our code do it. The model only handles the middle step. It proposes, and we decide whether to run it. That separation is what lets us add limits, permissions, and recovery later without rewriting the loop."

---

## Common mistakes

- **Letting the model run things directly.** It only proposes. Your code executes.
- **Forgetting to save the proposal in history.** The model then sees a result with no request. It gets confused.
- **Crashing on a bad proposal.** A wrong tool name is normal. Send the error back as data so the model can adjust.
- **Mixing perceive into the loop body.** It feels tiny now. Later it's where half the hard problems live. Keep it separate.
- **Not printing the steps.** Without a trace you're debugging blind.
