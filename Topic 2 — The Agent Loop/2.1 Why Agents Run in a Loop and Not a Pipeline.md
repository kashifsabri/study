

Making a sandwich from a recipe card: bread, cheese, close it. You know every step before you start. That is a **pipeline**.

Finding your lost shoe: look under the bed. Not there. Look in the hall. Not there. Ask your sister. Each step depends on what you just found out. You cannot write the steps down ahead of time. That is a **loop**.

An agent is the shoe-finder. It does one thing, looks at what happened, and only then picks the next thing.

---

## Simple technical version

The whole difference is **who decides the steps, and when**.

```
PIPELINE  (programmer decides, before the run)

  input ──▶ step 1 ──▶ step 2 ──▶ step 3 ──▶ output
            (always)   (always)   (always)


LOOP  (the model decides, during the run)

         ┌─────────────────────────────────────────┐
         ▼                                         │
   look at what we know ──▶ ask the model          │
                                │                  │
                    ┌───────────┴───────────┐      │
                    ▼                       ▼      │
              "here's the answer"     "run this tool"
                    │                       │      │
                  STOP                 runtime runs it
                                            │      │
                                    result goes back
                                    in as DATA ────┘
```

Why can't we just plan the steps first? One fact: **the model cannot see the future.** It doesn't know if a search will find anything, if a file exists, or if a tool will break. It only learns by trying. So step 4 has to wait for the result of step 3.

|Question|Pipeline|Loop|
|---|---|---|
|Who picks the steps?|The programmer, before the run|The model, during the run|
|How many steps?|Fixed|Unknown until it ends|
|A step gives a surprise|Breaks, or passes junk along|The next step reacts to it|
|What stops it?|Reaching the last step|A rule the runtime enforces|
|Best for|Same path every time|Path depends on what you find|

### Five things that follow from "it's a loop"

|Thing|What it means|What goes wrong if you ignore it|
|---|---|---|
|The model forgets|It remembers nothing between calls. Your code resends the history every time|Model acts confused, starts over each step|
|The loop must be capped|Nothing stops the model from proposing tools forever|Infinite loop, real invoice|
|Tool output is data|A fetched page may say "ignore your rules". That is text to read, never an order|Model obeys a stranger's web page|
|Any step can fail|Bad JSON, timeout, crash between "ran the tool" and "wrote it down"|Demo works, real use breaks|
|Crash means "unknown"|Process died after calling a payment tool. Did it pay? Your own notes can't say|Double payment, or a payment you never recorded|

## Code

### Same question, pipeline vs loop

The model here is fake and follows a script, so you can run it for free and see the shape.

```python
# ---- fake tool: first query finds nothing ON PURPOSE ----
# Real life does this to you. The point is to show a surprise.
def search(query):
    if query == "capital of Australia":
        return "no results"
    return "Canberra is the capital of Australia."

TOOLS = {"search": search}


# ---- fake model: looks at the LAST message and proposes something ----
def fake_model(history):
    last = history[-1]
    if last["role"] == "user":
        return {"type": "tool", "tool": "search",
                "args": {"query": "capital of Australia"}}
    if last["content"] == "no results":
        # Surprise. A pipeline is stuck here. A loop can change its mind.
        return {"type": "tool", "tool": "search",
                "args": {"query": "Australia capital city Canberra"}}
    return {"type": "answer", "text": last["content"]}


def pipeline(question):
    # Steps fixed in code. It cannot react to "no results".
    return search("capital of Australia")


def loop(question, max_steps=5):
    # WHY history: the model forgets everything between calls.
    # This list IS its memory. We resend it every time.
    history = [{"role": "user", "content": question}]

    # WHY a bounded for-loop and not "while True":
    # nothing forces the model to stop. We must.
    for _ in range(max_steps):
        reply = fake_model(history)

        if reply["type"] == "answer":
            return reply["text"]

        # WHY we run the tool, not the model:
        # the model only PROPOSED it. Our code decides whether to run it.
        result = TOOLS[reply["tool"]](**reply["args"])

        # WHY role "tool": this is data for the model to read,
        # not an instruction for it to follow.
        history.append({"role": "tool", "content": result})

    # WHY raise: running out of steps is a failure. It must be loud.
    raise RuntimeError("ran out of steps")


print("pipeline:", pipeline("Capital of Australia?"))
print("loop:    ", loop("Capital of Australia?"))
```

```
pipeline: no results
loop:     Canberra is the capital of Australia.
```

### Break it on purpose

Make the model never answer, and watch the cap save you:

```python
def stubborn_model(history):
    # Always proposes another search. Never answers.
    return {"type": "tool", "tool": "search", "args": {"query": "again"}}

# Swap fake_model for stubborn_model inside loop(), run it:
# -> RuntimeError: ran out of steps
```

Without `max_steps`, this runs forever. That one line is the whole reason budgets exist later.

## Real-life examples

### How Claude does it

When I search the web for you, that's a loop. I search, read what came back, decide it's not enough, and search again with different words. I don't know beforehand how many searches it will take. It depends on what I find.

Three things are true for me right now:

- I don't remember anything between calls by myself. The conversation gets resent each time.
- I never see a website. I only see the text a tool hands back, and I treat it as data. If a page says "ignore your instructions", I tell you about it. I don't obey it.
- I'm capped. I can't propose tool calls forever.

### How ChatGPT does it

ChatGPT running code is the same loop, and you can watch it. It writes code, runs it, sees an error, fixes the code, runs it again. The number of rounds is unknown at the start. Agent mode with a browser does the same thing on the live web: look at the page, click, look again, click again.

### In real products

|Product|Loop looks like|Loop or pipeline?|
|---|---|---|
|Coding agent (Claude Code, Cursor)|read file, edit, run tests, see failure, edit again|Loop|
|Support agent with a refund tool|look up order, decide, maybe refund, confirm|Loop|
|Plain chatbot, no tools|one question, one answer|Pipeline of length one|
|Nightly report script|pull data, make chart, send email|Pipeline. Do not make this an agent|

## Where this lands in our build

1. **The loop is the whole build.** Every later piece exists to make this one circle safe: limits, a record of every step, a rule on what may run, surviving a crash.
2. **`max_steps` is a placeholder.** A plain counter breaks the first time we replay a run. It becomes a proper budget (steps, tokens, cost, time) that survives a restart.
3. **`history` in memory is not the truth.** If the process dies, the list is gone. In the real build the durable event log is the truth and history is rebuilt from it.
4. **`role: "tool"` becomes a labeled fragment.** Tool output gets marked data-only, enforced in one place when the model input is built.
5. **Target agent (still open).** Use the decision flow above on its tasks. Any task where you can write the steps down is a pipeline and doesn't need this runtime.

## Say it to your manager

> "A pipeline has fixed steps. An agent can't, because it doesn't know what a tool will return until it calls it. So it loops: act, look, decide. The price is that the loop can run forever and can fail halfway. So we cap it and record every step. Most of our runtime exists to make that loop safe. And if a task has the same steps every time, we shouldn't use an agent."

---

## Common mistakes

- **Using a loop when a pipeline would do.** More cost, more latency, more ways to fail.
- **Trusting the model to stop.** The runtime sets the limit.
- **Thinking the model remembers.** It doesn't. No history resent, no memory.
- **Calling a fixed chain of model calls "an agent".** If the programmer picked every step, it's a pipeline with a model inside.
- **Treating the loop as one big function call.** It's many steps. Each can fail alone and must be recorded alone.
