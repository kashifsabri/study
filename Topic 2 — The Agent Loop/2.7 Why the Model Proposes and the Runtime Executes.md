

At a restaurant, you tell the waiter what you want. You don't walk into the kitchen and cook it yourself.

You say "I'd like a pizza." That's a **request**. The kitchen decides: do we have dough? Is this on the menu? Are you allowed to order this? Only then does someone make the pizza.

The model is the customer. It can only ask. The runtime is the kitchen. It decides, and it's the only one with hands.

---

## Simple technical version

A language model reads text and writes text. That's all it does. It has no hands.

So when it "calls a tool," what it really wrote is a sentence that means: _"I would like `send_refund` run with these inputs."_ That sentence is a **proposal**. Nothing has happened yet.

```
   MODEL                        RUNTIME                        WORLD
   (words only)                 (has the hands)

   "I'd like send_refund  ───▶  1. is that a real tool?
    with order A17, 500"        2. are the inputs valid?
                                3. is this allowed?
                                4. any budget left?
                                5. write down "about to do it"
                                6. RUN IT  ────────────────────▶  refund happens
                                7. write down the result  ◀───────  result
                        ◀────   8. send result back as data
```

The gap between the model's sentence and step 6 is where **everything interesting in this project lives**: checks, limits, approval, records, recovery, and eventually TinySeal.

### The web server comparison

A web server never trusts a form just because someone submitted it. It checks the fields, checks who you are, checks what you may do. The proposal is the same. It's input to our runtime, and input gets validated.

One more reason to be careful: the model reads untrusted text (web pages, files). That text can push the model toward proposing something bad. So a proposal is not "what the user wants." It's "what the model, after reading who-knows-what, is asking for."

### Three designs, and who really decides

|Design|What happens|Who really decides|Problem|
|---|---|---|---|
|Model executes|Model has a shell or credentials and just does it|The model|Whatever it's talked into, it does|
|Rubber-stamp runtime|Runtime parses the request and runs it, no checks|Still the model|It looks like a gap, but nothing is in it|
|Real gap|Runtime validates, checks policy, records intent, then runs|The runtime|Costs extra code. Worth it|

Row two is the tricky one. If your runtime runs whatever parsed cleanly, you didn't separate anything. You just added a middleman.

### What sits in the gap

|Check|Question it answers|If it says no|
|---|---|---|
|Known tool|Does this tool exist?|Refuse, send error back|
|Valid inputs|Right names and types?|Refuse, send error back|
|Policy|Is this allowed here, for this user?|Refuse, or ask a human|
|Budget|Can we afford another step?|Stop the run|
|Intent record|Did we write down "about to do it" first?|Don't run|
|Timeout and cancel|Can we stop it if it hangs?|Cut it off, record unknown|

### What this does NOT protect against

If the model is tricked into proposing something that is valid **and** allowed, the gap lets it through. That's why the policy layer should be strict about what each agent may ever do (small permissions), so a tricked model has little to be tricked into.

## Code

Every proposal goes through the gap. Only some come out the other side.

```python
from dataclasses import dataclass
from typing import Callable

@dataclass(frozen=True)
class ToolDef:
    name: str
    effect: str          # read | create | update | delete | external
    params: dict         # argument name -> required type
    fn: Callable


def read_file(path):               return f"contents of {path}"
def send_refund(order_id, amount): return f"refunded {amount} on {order_id}"
def delete_file(path):             return f"deleted {path}"

# WHY the runtime owns this list: the model can only ASK for names on it.
# It never gets a shell, a password, or a way to run something not listed.
TOOLS = {
    "read_file":   ToolDef("read_file",   "read",     {"path": str}, read_file),
    "send_refund": ToolDef("send_refund", "external", {"order_id": str, "amount": int}, send_refund),
    "delete_file": ToolDef("delete_file", "delete",   {"path": str}, delete_file),
}


def validate_args(tool, args):
    # WHY validate: the model's text is INPUT to us, like a web form.
    for name, typ in tool.params.items():
        if name not in args:
            return f"missing {name}"
        if not isinstance(args[name], typ):
            return f"{name} must be {typ.__name__}"
    return None


def policy(tool):
    # WHY this is its own function: later this is where TinySeal plugs in.
    # Today it is one rule. The SHAPE (proposal in, decision out) is what matters.
    if tool.effect in ("external", "delete"):
        return "ask"
    return "allow"


def execute(run_id, step, proposal, log):
    name, args = proposal["tool"], proposal["args"]

    tool = TOOLS.get(name)
    if tool is None:
        # WHY return text and not crash: a bad proposal is normal.
        # The model reads this and can change its mind.
        return f"refused: no tool called '{name}'"

    problem = validate_args(tool, args)
    if problem:
        return f"refused: bad arguments ({problem})"

    if policy(tool) != "allow":
        return f"not run: '{name}' needs approval ({tool.effect})"

    # WHY write intent BEFORE running, with a dedup key:
    # if the process dies during the call, this line is the only proof
    # we were about to do it. The key lets the outside system ignore a repeat.
    dedup_key = f"{run_id}:{step}:{name}"
    log.append({"event": "ToolCallIntended", "tool": name,
                "args": args, "dedup_key": dedup_key})

    result = tool.fn(**args)                 # the ONLY line that touches the world

    log.append({"event": "ToolCompleted", "dedup_key": dedup_key,
                "result": result})
    return result


proposals = [
    {"tool": "read_file",   "args": {"path": "notes.txt"}},
    {"tool": "format_disk", "args": {}},
    {"tool": "send_refund", "args": {"order_id": "A17", "amount": "lots"}},
    {"tool": "send_refund", "args": {"order_id": "A17", "amount": 500}},
    {"tool": "delete_file", "args": {"path": "notes.txt"}},
]

log = []
for i, p in enumerate(proposals, 1):
    print(f"{i}. {p['tool']:<12} -> {execute('run1', i, p, log)}")

print()
for event in log:
    print(event)
```

```
1. read_file    -> contents of notes.txt
2. format_disk  -> refused: no tool called 'format_disk'
3. send_refund  -> refused: bad arguments (amount must be int)
4. send_refund  -> not run: 'send_refund' needs approval (external)
5. delete_file  -> not run: 'delete_file' needs approval (delete)

{'event': 'ToolCallIntended', 'tool': 'read_file', 'args': {'path': 'notes.txt'}, 'dedup_key': 'run1:1:read_file'}
{'event': 'ToolCompleted', 'dedup_key': 'run1:1:read_file', 'result': 'contents of notes.txt'}
```

Five proposals came in. One ran. The four that didn't run left **nothing** in the log as a tool call, because nothing happened.

### Break it on purpose

1. Change `policy` to always return `"allow"`. Run again. Proposals 4 and 5 now go through, and nothing else stopped them. One function was the only thing standing between "asked" and "did."
2. Move the `ToolCallIntended` append to _after_ `tool.fn(...)`. It looks the same on a happy run. Now imagine the process dies inside `tool.fn`: the log has no trace that a refund was attempted. That's the crash-mid-side-effect case.
3. Replace `TOOLS.get(name)` with `TOOLS[name]` and run proposal 2. The runtime crashes on a nonsense tool name. A wrong proposal should be an observation, not a crash.

## Real-life examples

### How Claude does it

I can't run anything. I write a request for a tool, and the system around me decides. In some products it stops and asks you "allow this?" That prompt is the gap made visible. When a fetched web page tries to give me orders, I treat it as data and mention it to you, and I still have no hands of my own.

### How ChatGPT does it

Same shape. When ChatGPT's agent mode asks you to confirm before a purchase or before logging in somewhere, that's the gap. The model proposed. The system said "not without a human."

### Temporal, the prior art for us

In Temporal, your workflow code doesn't do the side effect itself. It asks the engine to run a piece of work, and the engine runs it and writes the result into the history. That is the same split: one side proposes, the other side executes and records.

### In real products

|Product|What the gap looks like|
|---|---|
|Coding agent|Shell commands run only if on an allow list, or after you click approve|
|Support agent|Refunds under a limit run; larger ones wait for a human|
|Browser agent|Reading a page is free; submitting a form asks first|

## Where this lands in our build

1. **`ActionProposal` and `ToolCall` are two separate types.** The proposal is what the model asked for. The call is what the runtime decided to do after checking. They have different fields and different lifetimes.
2. **The policy check gets a real seam.** It's a do-nothing "allow" at first, but every proposal goes through it. TinySeal replaces it at the end. If the seam is there from the start, that final step is a plug and not a rewrite.
3. **Intent is written before effect.** `ToolCallIntended` with a dedup key goes into the log before any tool runs. An intent with no matching outcome triggers that tool's recovery path.
4. **Tool properties drive the gap.** Each tool declares what it does, whether repeating it is safe, and whether it can be undone. The recovery rule is derived from those, not typed in by hand.
5. **The model provider never imports the tool runner.** Keep them in separate modules. If a model-provider file ever imports the executor, something is wrong.
6. **Refusals are observations.** They go back to the model as data and count as part of a step.
7. **Human approval is an outcome of the gap.** It becomes a proper waiting state later, one that survives a restart.
8. **Target agent (still open).** List its tools and mark each one: read (free), or does it change something? Every "changes something" tool needs a decision now about who approves it.

**Log this in DECISIONS.md now:** "ActionProposal and ToolCall are separate types. Reason: the proposal is what the model asked for, the call is what the runtime decided to do. The gap between them has a name and a place for checks."

## Common mistakes

- **A rubber-stamp runtime.** If everything that parses gets run, nothing was separated.
- **Giving the model a shell or credentials directly.** Then it can do anything it's talked into.
- **Validating after running.** Too late.
- **Putting the policy check inside each tool.** It gets forgotten in one of them. Keep it in one place, before execution.
- **Assuming a valid proposal is a safe one.** Valid and allowed can still be harmful. Keep permissions small.
- **Crashing on a bad proposal.** Send a refusal back as an observation.
