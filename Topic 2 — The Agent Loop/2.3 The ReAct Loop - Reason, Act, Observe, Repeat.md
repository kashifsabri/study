

You're fixing a bike that won't go.

1. **Think out loud:** "The chain might be loose."
2. **Do something:** you check the chain.
3. **See what happened:** "The chain is fine. The tire is flat."
4. **Think again:** "So it's the tire."

You never just do things silently. You say why, you do it, you look at what came back, and you say why again. That's ReAct. **Re**ason, then **Act**, then look, then go around again.

---

## Simple technical version

ReAct is the minimal loop with two upgrades:

1. The model writes a short **thought** before every action.
2. What comes back is a named piece of the loop, the **observation**, not just "some text in history."

```
   ┌────────────────────────────────────────────┐
   ▼                                            │
 THOUGHT   "I need to find who wrote Hamlet."   │
   │       (the model writes a short note)      │
   ▼                                            │
 ACTION    search[who wrote Hamlet]             │
   │       (a proposal, the runtime decides)    │
   ▼                                            │
 OBSERVATION  "William Shakespeare wrote..."    │
   │       (data from the world, never orders)  │
   └────────────────────────────────────────────┘

 ...until the model proposes: finish[the answer]
```

|Question|Minimal loop|ReAct loop|
|---|---|---|
|What does the model write each turn?|A proposal|A thought, then a proposal|
|Is there a name for what tools return?|"tool result in history"|Observation, a named part of the loop|
|Is finishing special?|Reply type "answer"|Can be just another action: `finish[...]`|
|Can you see why the model chose the action?|Only by guessing|The thought is right there|

### Why the thought helps

Two reasons, both plain:

- **For the model:** writing "I need his birth year next" before acting makes it more likely to pick the right next action. Thinking in text steers the next text.
- **For you:** when a run goes wrong, the thoughts tell you where its reasoning went off.

### One warning about thoughts

A thought is a note the model wrote. It is **not proof** and it is **not a command**. The model can write a confident thought that is wrong. Our runtime never runs anything because a thought said so. Only the action counts, and even the action is only a proposal.

### The memory is one growing transcript

In ReAct every turn is added to one long text. The model reads all of it again each time, because it forgets everything between calls.

```
Question: Who wrote Hamlet and when was he born?
Thought: I need to find who wrote Hamlet.
Action: search[who wrote Hamlet]
Observation: William Shakespeare wrote Hamlet.
Thought: Now I need his birth year.
Action: search[William Shakespeare birth year]
Observation: William Shakespeare was born in 1564.
Thought: I have both facts.
Action: finish[William Shakespeare, born 1564]
```

Each turn makes the transcript longer. Longer means more tokens, which means more money and slower calls. Keep that in mind, it comes back later.

## Code

A small ReAct agent. The model is fake and follows a script, so it runs for free. The important part is the **parser**, because in ReAct the model's reply is plain text and we have to read it.

```python
import re

# ---------- tool ----------
def search(query):
    q = query.lower()
    if "hamlet" in q:
        return "William Shakespeare wrote Hamlet."
    if "shakespeare" in q:
        return "William Shakespeare was born in 1564."
    return "no results"

TOOLS = {"search": search}


# ---------- fake model ----------
# Reads the whole transcript and writes the next Thought + Action.
# It counts Observation lines to know where it is in the script.
def fake_model(transcript):
    seen = transcript.count("Observation:")
    if seen == 0:
        return "Thought: I need to find who wrote Hamlet.\nAction: search[who wrote Hamlet]"
    if seen == 1:
        return "Thought: Now I need his birth year.\nAction: search[William Shakespeare birth year]"
    return "Thought: I have both facts.\nAction: finish[William Shakespeare, born 1564]"


# ---------- the loop ----------
def run(question, max_steps=6):
    # WHY one string: the model forgets between calls, so we resend
    # the whole story every time. This string IS the memory.
    transcript = f"Question: {question}\n"

    for step in range(1, max_steps + 1):
        reply = fake_model(transcript)
        print(f"--- step {step}\n{reply}")
        transcript += reply + "\n"

        # WHY a parser: the model returns TEXT. We must find the
        # action inside it. Real models get this wrong sometimes.
        match = re.search(r"Action:\s*(\w+)\[(.*)\]", reply)

        if not match:
            # WHY an observation and not a crash: bad output is normal.
            # Tell the model what went wrong and let it try again.
            observation = "error: reply had no 'Action: tool[input]' line"
        else:
            name, arg = match.groups()

            if name == "finish":
                # WHY finish is an action: ending is also a proposal.
                # The model says "I'm done", and our code stops the loop.
                return arg

            if name not in TOOLS:
                observation = f"error: no tool called '{name}'"
            else:
                observation = TOOLS[name](arg)

        print(f"Observation: {observation}")
        transcript += f"Observation: {observation}\n"

    # WHY raise: not finishing in time is a failure, so make it loud.
    raise RuntimeError("ran out of steps")


print("ANSWER:", run("Who wrote Hamlet and when was he born?"))
```

```
--- step 1
Thought: I need to find who wrote Hamlet.
Action: search[who wrote Hamlet]
Observation: William Shakespeare wrote Hamlet.

--- step 2
Thought: Now I need his birth year.
Action: search[William Shakespeare birth year]
Observation: William Shakespeare was born in 1564.

--- step 3
Thought: I have both facts.
Action: finish[William Shakespeare, born 1564]
ANSWER: William Shakespeare, born 1564
```


### Break it on purpose

Make the model forget the action line. Change the first reply in `fake_model` to:

```python
return "I think it was Shakespeare."
```

What you'll see: the parser finds no action, an error observation is written into the transcript, and the loop keeps going. Since this fake model counts observations, it then carries on with its script. A real model would read the error and fix its format.

Now the second break. Remove the `finish` branch's `return`. The loop never ends and `max_steps` stops it. That is the cap doing its job.

## Real-life examples

### How Claude does it

When I search for you, it goes reason, act, observe, repeat. I decide a search is needed, I request it, the results come back as data, and I decide again.

One difference from the paper version: modern setups don't make me type `Action: search[...]` in plain text. Tool requests come as structured data, and my reasoning can be kept separate from the visible reply. The loop shape is the same. Only the format changed. That makes parsing errors rarer, but not gone. Structured output can still come back malformed.

### How ChatGPT does it

Same shape. It reasons, calls a tool such as browsing or running Python, gets the result, and reasons again. Products show this as "Searching..." or "Analyzing..." steps. Each of those is one trip around the circle.

### In real products

|Product|Thought (reason)|Action|Observation|
|---|---|---|---|
|Coding agent|"Tests failed in auth.py, look there"|Read auth.py|The file contents|
|Support agent|"Need order status first"|Call order lookup|Status: shipped|
|Research agent|"First search didn't help, rephrase"|Search again|New results|

ReAct comes from a 2022 paper (Yao et al.). It's the base pattern almost every tool-using agent still follows.

## Where this lands in our build

1. **ReAct is our default loop.** The roadmap says fancier strategies (planning, splitting tasks, reflection) must beat a plain ReAct loop on our own tests before they get added. So build this one well and measure it. Don't skip ahead.
2. **Observation is its own kind of record.** It gets its own event in the log, and its content is marked data-only so it can never give orders.
3. **The parser lives in the model provider, not in the loop.** Malformed replies, retries, and repair belong to the model provider hardening work. The loop should only ever see a clean proposal.
4. **Thoughts are stored but never trusted.** They go in the log so we can answer "why did it do that?" later. Nothing runs because of a thought.
5. **Long transcripts cost money.** Every turn resends everything. That's why the budget tracks tokens, and why the context builder later has to decide what to drop.
6. **Target agent (still open).** Write out one full ReAct run for it on paper, in the transcript format above. If you can't imagine the observations, the tools aren't clear yet.

## Say it to your manager

> "ReAct means the model writes a short thought, proposes one action, our code runs it, and the result comes back as an observation. Then it repeats. It's the base pattern for tool-using agents. The thought helps the model choose well and helps us debug, but only the proposed action matters, and our runtime still decides whether to run it. We'll only add anything fancier if our own tests show it beats this."

## Common mistakes

- **Trusting the thought.** It's a note, not a fact and not a command.
- **Crashing when the reply can't be parsed.** Return an error observation, or repair it in the model provider.
- **Treating the observation as instructions.** It's data from the world, always.
- **Letting the transcript grow forever.** Cost and delay go up with every turn.
- **Adding planning before measuring plain ReAct.** You won't know if it helped.
