

You're looking for your shoe. There are only a few ways it ends:

- You **find the shoe.** Done, happy.
- Your mom says **"time's up, we're leaving."** You stop, shoe or no shoe.
- You **fall and hurt your foot.** You can't keep going.

Notice who decides. You decide when you find it. But mom decides when time's up, and she doesn't ask you. An agent's loop ends the same way: sometimes the model says "done," and sometimes the runtime stops it whether the model likes it or not.

---

## Simple technical version

A loop with no exit is a bug. Every run must end in exactly one way, and we must be able to say which.

```
                 after every step, ask in this order
                              │
                              ▼
                  ┌─ was it cancelled? ────────▶ CANCELLED
                  │
                  ├─ any budget left? ── no ───▶ FAILED (budget_exceeded)
                  │        │
                  │       yes
                  │        ▼
                  │   call the model
                  │        │
                  │   ┌────┴────────────┐
                  │   ▼                 ▼
                  │ "answer"       "run this tool"
                  │   │                 │
                  │   ▼                 ▼
                  │ COMPLETED       run it
                  │ (goal_met)          │
                  │              ┌──────┴───────┐
                  │              ▼              ▼
                  │           worked         can't recover
                  │              │              │
                  └──────────────┘              ▼
                  (go around again)          FAILED (tool_failure)
```

The endings:

|Ending|Who decides|Final status|Reason recorded|
|---|---|---|---|
|Goal met|The model says "done", the runtime accepts|COMPLETED|goal_met|
|Budget exhausted|The runtime, without asking the model|FAILED|budget_exceeded|
|Failure|The runtime, when recovery isn't possible|FAILED|tool_failure, model_invalid_output, and so on|
|Cancelled|The user or the system|CANCELLED|cancelled|

### Three things to notice

**1. "Done" is the model's opinion.** The model says "here's the answer." That doesn't mean the answer is right or the task is finished. Right now we accept it. Later, a check on the answer can be added, but only if our own tests show we need it.

**2. Budget is checked BEFORE spending, not after.** If you check after the model call, you've already paid for the call that broke the limit. Check first, then spend.

**3. Running out of budget is a failure with a reason. Not a silent stop.** The user must be able to tell "it gave up," "it hit the limit," and "it broke" apart. Three different situations, three different reasons.

### Not every stop is final

Two more states will appear later: **waiting** (the agent asked a human something and is paused) and **paused**. They aren't endings. The run comes back. Keep them out of your head for the three endings above.

### Getting stuck in circles

The model can propose the same failing action again and again. Nothing about that breaks a rule. The budget will eventually stop it, but that can be expensive. A repeat detector could stop it early. We don't add one now. First measure how often it happens in our own tests, then decide.

## Code

One loop, four different endings. Each ending returns a result with a status **and** a reason.

```python
from dataclasses import dataclass
from typing import Optional

class ToolFailure(Exception):
    """A tool broke in a way we can't recover from."""


@dataclass(frozen=True)
class RunResult:
    status: str                 # completed | failed | cancelled
    reason: str                 # WHY it ended. Never leave this blank.
    steps_used: int
    answer: Optional[str] = None


def ok_tool():     return "fine"
def broken_tool(): raise ToolFailure("payment service down")
TOOLS = {"ok": ok_tool, "broken": broken_tool}


def run(model, max_steps=4, cancelled=lambda: False):
    history = [{"role": "user", "content": "do the task"}]

    # WHY the loop condition IS the budget check:
    # range() decides BEFORE each step whether another one is allowed.
    # We never start a step we aren't allowed to finish.
    for step in range(1, max_steps + 1):

        # WHY cancel is checked first: if the user said stop,
        # we shouldn't spend another model call to find out.
        if cancelled():
            return RunResult("cancelled", "cancelled", step - 1)

        proposal = model(history)

        if proposal["type"] == "answer":
            # The model said "done". We accept it and record why we stopped.
            return RunResult("completed", "goal_met", step, proposal["text"])

        try:
            result = TOOLS[proposal["tool"]](**proposal["args"])
        except ToolFailure:
            # WHY return and not raise: a failed run is a normal outcome
            # that we record. It must produce a result, not a stack trace.
            return RunResult("failed", "tool_failure", step)

        history.append({"role": "tool", "content": result})

    # We only get here if every step was used and the model never answered.
    # WHY this is FAILED and not "completed with a partial answer":
    # a run that ran out of budget did not do the job. Say so.
    return RunResult("failed", "budget_exceeded", max_steps)


# ---- three fake models, one per ending ----
def finisher(history):
    if len(history) == 1:
        return {"type": "tool", "tool": "ok", "args": {}}
    return {"type": "answer", "text": "done"}

def endless(history):
    return {"type": "tool", "tool": "ok", "args": {}}      # never answers

def breaker(history):
    return {"type": "tool", "tool": "broken", "args": {}}  # tool will blow up


def show(r):
    print(f"{r.reason:<16} {r.status:<10} steps={r.steps_used}  answer={r.answer}")

show(run(finisher))
show(run(endless))
show(run(breaker))
show(run(finisher, cancelled=lambda: True))
```

```
goal_met         completed  steps=2  answer=done
budget_exceeded  failed     steps=4  answer=None
tool_failure     failed     steps=1  answer=None
cancelled        cancelled  steps=0  answer=None
```

### Break it on purpose

1. Delete `max_steps` from the `for` and use `while True`. Run `endless`. It never returns. That's the infinite loop with a real invoice attached.
2. In `endless`, look at `budget_exceeded` and ask: at which step did we stop, and was a model call wasted? (Answer: none. The check ran before step 5 could start.)
3. Replace `RunResult("failed", "budget_exceeded", ...)` with `RunResult("completed", "goal_met", ...)`. Everything still "works," but now a run that gave up looks like a success. That's the mistake to avoid.

## Real-life examples

### How Claude does it

I stop in one of these ways: I write an answer instead of asking for a tool, or the system around me stops me because of a limit, or you cancel. I don't decide the limits. If I hit one, the honest thing is to tell you that I ran out of room, not to present a half-finished job as done.

### How ChatGPT does it

Same three exits. Long agent tasks can stop at a time or step limit and report that they couldn't finish. You can also press stop. The point is that the product says which one happened, so you know whether to trust the result.

### In real products

|Product|Normally ends when|Stopped by the system when|What a good product shows|
|---|---|---|---|
|Coding agent|Tests pass and it says done|Max turns reached|"Stopped at limit" and what's left|
|Support agent|Reply sent|Refund tool keeps failing|"Escalated to a human", not silence|
|Research agent|Report written|Cost or time cap hit|"Partial. Ran out of budget"|

## Where this lands in our build

1. **Every run ends with exactly one terminal event and one machine-readable reason.** A completed run and a failed run each get their own event, and the reason is stored, not guessed later.
2. **This is the lifecycle state machine.** COMPLETED, FAILED, and CANCELLED are terminal. Once there, the run can't go anywhere. Trying to complete a failed run is refused at write time.
3. **The step counter here becomes the budget ledger.** A ledger reserves before spending and settles after, and survives a restart. A plain counter breaks on replay.
4. **The `except ToolFailure` becomes the failure table.** Each error type gets a row: retry, retry with repair, replan, escalate, or fail. Written as a table so it doesn't drift.
5. **Cancel needs rules for in-flight work.** If a tool is already running when the user cancels, do we wait, or kill it? That decision is part of the tool system.
6. **"Done" isn't checked yet.** Verifying the answer is later work and it is gated by our own evaluation results. Don't build it now.
7. **Target agent (still open).** Write its success criteria in one sentence. If you can't, the model will decide when it's done, and nothing will check.

## Common mistakes

- **No cap on the loop.** The model will not reliably stop itself.
- **Checking the budget after spending.** You've already paid for the step that broke the limit.
- **Calling a budget stop "completed."** It didn't finish. Mark it failed with a reason.
- **One vague "failed" for everything.** You can't fix what you can't tell apart.
- **Believing "done" means correct.** It's the model's opinion.
- **Ignoring cancel.** A user pressing stop must actually stop the run.
