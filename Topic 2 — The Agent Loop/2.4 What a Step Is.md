

Think of a board game. One **turn** is: you roll, you move, you see where you landed. Then it's the next turn.

You don't say "I rolled" is one turn and "I moved" is another turn. The whole roll-move-look is one turn. You count turns, you can point at turn 7, and if the doorbell rings you can say "we stopped on turn 7."

A **step** is one turn of the agent's loop.

---

## Simple technical version

One step = **one trip around the loop**:

```
              ┌─────────────── ONE STEP ───────────────┐
              │                                        │
  build  ──▶  │  model call ──▶ proposal ──▶ run it ──▶ observation  │
  input       │                                        │
              └────────────────────────────────────────┘
                                 │
                        next step starts here
```

That sounds obvious. The hard part is picking the boundary, because the choice decides what you count, log, limit, and recover.

|Option|One step is...|Problem|
|---|---|---|
|A. Each model call|Only the asking|A tool run falls between steps. Crash there and no step owns it|
|B. Each tool call|Only the doing|A model call that answers has no step. Can't count it|
|C. One full trip (model call + handling the proposal + observation)|The whole turn|One catch: what if the model asks for two tools at once? (open question below)|

Option C is the one to use. A step owns everything that happened in that turn, so it's the natural unit to count, log, cap, and recover.

### Where a step sits

```
Session (the whole conversation with one user)
  └─ Turn (one user message and the agent's full reply to it)
      └─ Run (one attempt to finish that turn)
          └─ Step (one trip around the loop)
              └─ Events (the small facts inside it:
                            model asked, model replied,
                            tool intended, tool done,
                            observation recorded.)
```

A step is not an event. A step is a **group** of events. Events are the small facts that got written down. The step is the label that says "these belong together."

### What a step needs to carry

|Field|What it holds|Why it matters|
|---|---|---|
|Index|1, 2, 3...|The logical clock. Replay needs "step 4", not "4:32 pm"|
|Status|started, done, failed|A step stuck on "started" means we don't know what happened|
|Proposal|What the model asked for|Debugging: what did it want?|
|Observation|What came back|The next step reads this|
|Tokens and cost|What it used|Feeds the budget|
|Times|Start and end|Latency, per step|

### Two clocks

A step has a wall time (when it happened) and an index (which step it was). They're different. If you replay a run tomorrow, the wall time is wrong but "step 4" is still step 4. Anything that has to be reproduced uses the index.

## Code

We record a step **before** doing its work, then update it after. Then we simulate a crash and see what the record shows.

```python
import time
from dataclasses import dataclass
from typing import Optional

@dataclass
class Step:
    index: int                        # logical clock: 1, 2, 3...
    started_at: float                 # wall clock: only for humans
    proposal: Optional[dict] = None
    observation: Optional[str] = None
    status: str = "started"           # started | done
    finished_at: Optional[float] = None


def multiply(a, b): return a * b
def add(a, b):      return a + b
TOOLS = {"multiply": multiply, "add": add}


# fake model (kept short: it only reads the tool results)
def reason(history):
    results = [m["content"] for m in history if m["role"] == "tool"]
    if not results:
        return {"type": "tool", "tool": "multiply", "args": {"a": 12, "b": 7}}
    if len(results) == 1:
        return {"type": "tool", "tool": "add",
                "args": {"a": int(results[0]), "b": 5}}
    return {"type": "answer", "text": f"The result is {results[-1]}"}


def run(question, steps, crash_at=None, max_steps=6):
    history = [{"role": "user", "content": question}]

    for i in range(1, max_steps + 1):
        step = Step(index=i, started_at=time.time())

        # WHY record the step BEFORE any work:
        # if the process dies mid-step, this half-filled record is the
        # only evidence that the step began. No record = no clue.
        steps.append(step)

        proposal = reason(history)
        step.proposal = proposal

        if proposal["type"] == "answer":
            step.observation = proposal["text"]
            step.status = "done"
            step.finished_at = time.time()
            return

        result = str(TOOLS[proposal["tool"]](**proposal["args"]))

        # Imagine this tool is a payment. It has just RUN.
        # Now the process dies before we write the result down.
        if crash_at == i:
            raise SystemExit("process killed")

        step.observation = result
        step.status = "done"
        step.finished_at = time.time()
        history.append({"role": "tool", "content": result})


def show(steps):
    for s in steps:
        what = "-"
        if s.proposal:
            what = s.proposal.get("tool", s.proposal["type"])
        obs = s.observation if s.observation is not None else "??? never recorded"
        print(f"step {s.index}  {s.status:<8} {what:<9} -> {obs}")


print("== normal run ==")
steps = []
run("What is 12 times 7, plus 5?", steps)
show(steps)

print("\n== crash during step 2 ==")
steps = []
try:
    run("What is 12 times 7, plus 5?", steps, crash_at=2)
except SystemExit:
    pass
show(steps)
```

```
== normal run ==
step 1  done     multiply  -> 84
step 2  done     add       -> 89
step 3  done     answer    -> The result is 89

== crash during step 2 ==
step 1  done     multiply  -> 84
step 2  started  add       -> ??? never recorded
```

Read that last line. Step 2 says `started`, has a proposal, and has **no observation**. The tool may have run. It may not have. **From this record alone, we cannot tell.** That's not a bug in the demo, it's the whole problem, and it's why the event log exists in the shape it does.

## Real-life examples

### How Claude does it

Each time I ask for a tool and get a result back, that's one trip. When you see me search three times in one answer, that's three steps, plus a last one where I write the reply. I don't count them myself. The system around me does.

### How ChatGPT does it

Same. Each "Searching..." or "Running code..." you see is roughly one step. The final message is the last step.

### In real products

|Product or system|What it calls the same idea|What it does with it|
|---|---|---|
|Agent SDKs and coding agents|"turn", "iteration", "max turns"|A cap on how many steps a run may take|
|Temporal (the prior art for us)|An "activity"|One unit of work with its own retry and its result written into the history|
|Support agent|One lookup or one refund attempt|Logged separately so a failed refund can be found|

Different names, same job: a unit you can count, cap, log, and recover.

## Where this lands in our build

1. **Step is a frozen contract.** Its shape gets fixed when we write the contracts. Once steps are saved, changing the shape is painful, so it needs a version number from the start.
2. **The step index is the logical clock.** Replay and recovery use "step 4", never wall time.
3. **The step limit counts these.** "Max steps" only means something once we've decided one step = one full trip. Decide it now.
4. **A step is a group of events.** The event log stores the small facts. The step is how they're grouped.
5. **The half-open step is the crash case.** A step that says `started` with no outcome triggers the recovery path. That's the "unknown outcome" idea, written as a real event and not swallowed as an error.
6. **Target agent (still open).** Write one run of it as steps: how many, and which ones touch the outside world?

## Say it to your manager

> "A step is one full trip around the loop: the model call, whatever it proposed, and the result. It's the unit we count for limits, group for logging, and point to when something goes wrong. We write the step down before doing its work, so if the process dies we can see exactly which step was in progress and that we don't know how it ended."

---

## Common mistakes

- **Counting only model calls.** Tool runs then belong to nobody.
- **Writing the step down only after it finishes.** A crash leaves no trace it ever started.
- **Using wall time as the order.** Replays and clock drift break it. Use the index.
- **Mixing up step and event.** Events are small facts. A step is the group.
- **Treating a half-finished step as "failed".** It's "unknown", which needs different handling.
