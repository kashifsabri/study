

Catching a ball needs three body parts:

- **Eyes** — you see the ball coming. That's **perception**.
- **Brain** — you decide "move my hands left." That's **reasoning**.
- **Hands** — you actually move them. That's **action**.

If any one fails, you drop the ball. And here's the thing people forget: **if your eyes were closed, it's not your brain's fault you missed it.**

Same with an agent. When it does something stupid, everyone blames the AI. Usually the AI just wasn't shown the right thing.

---

## Simple technical version

Every agent step does these three, in order, forever:

```
   PERCEPTION          REASONING            ACTION
   gather what          decide what          do it and
   the AI should  ───▶  to do next    ───▶   record it
   see                                          │
        ▲                                       │
        └───────────────────────────────────────┘
                  the result becomes
                  part of the next perception
```

|Part|What it really is|Who does it|
|---|---|---|
|**Perception**|Building the text you send to the AI|**Your code**|
|**Reasoning**|The AI reads it and replies|**The AI**|
|**Action**|Checking, running, and recording what it asked for|**Your code**|

### The big realization

> **Perception is your job, not the AI's.**

The AI has no eyes. It doesn't "look at" your files or your database. It only sees **the text you chose to put in front of it**.

So if your agent:

- ignores something important → you probably didn't include it
- uses old information → you included a stale copy
- obeys a malicious webpage → you included it without marking it as untrusted
- forgets what it did → you didn't include the history

All four of those look like "the AI is dumb." **None of them are reasoning failures.** They're perception failures — your code's failures.

### What goes wrong in each part

|Part|Typical failures|
|---|---|
|**Perception**|Missing info · stale info · too much info (doesn't fit) · untrusted text mixed in with your rules|
|**Reasoning**|Picks the wrong tool · invents facts · returns broken output · claims it's finished when it isn't|
|**Action**|Tool times out · runs twice · half-finishes · crashes before you recorded it|

Notice that **you own two of the three columns.**

## Code

### The three parts, made obvious

```python
def one_step(state):

    # ─── 1. PERCEPTION ────────────────────────────────
    # We decide what the AI is allowed to see. It sees nothing else.
    context = build_context(
        system_rules = state.rules,          # our orders     — may instruct
        history      = state.recent_steps,   # what happened  — data only
        tool_results = state.observations,   # what came back — data only
    )

    # ─── 2. REASONING ─────────────────────────────────
    # The only line the AI is involved in.
    reply = model.generate(context)

    # ─── 3. ACTION ────────────────────────────────────
    if reply.tool_call is None:
        return Finished(reply.text)

    check_tool_exists(reply.tool_call)        # validate
    check_allowed(reply.tool_call)            # permission
    check_budget(state)                       # limits

    log("about to run", reply.tool_call)      # record BEFORE doing it
    result = run_tool(reply.tool_call)
    log("finished", result)                   # record after

    state.observations.append(result)         # feeds the next perception
    return Continue(state)
```

Three blocks. The AI is **one line**. You wrote the other twenty.

### Why "perception is your job" is not just a slogan

Same AI, same question. Two different perception choices:

```python
# ❌ BAD PERCEPTION — no history included
context = [
    {"role": "system", "content": "You are a file assistant."},
    {"role": "user",   "content": "Delete the old logs."},
]
# The AI has no idea it already deleted them 2 steps ago.
# It deletes again, or gets confused and loops.
```

```python
# ✅ GOOD PERCEPTION — history included
context = [
    {"role": "system", "content": "You are a file assistant."},
    {"role": "user",   "content": "Delete the old logs."},
    {"role": "tool",   "content": "deleted logs/2024-*.txt (12 files)"},
]
# Now the AI can see the job is done and just answers.
```

**Identical model. Identical prompt. Completely different behaviour.** The difference is what your code chose to show it.

### And perception is where security lives

```python
def build_context(fragments):
    instruction_area = []
    data_area = []

    for f in fragments:
        if f.can_instruct:
            instruction_area.append(f)     # system rules, user request
        else:
            data_area.append(f)            # tool output, web pages, memory

    return render(
        instructions = instruction_area,
        data         = data_area,          # clearly separated & labelled
    )
```

A fetched webpage saying _"ignore your instructions"_ never reaches the instruction area. Not because we asked the AI nicely, but because **the code physically won't put it there.**

## Real-life examples

### How Claude does it

- **Perception** = my context: the rules I'm given, our conversation, and whatever tools returned.
- **Reasoning** = generating this reply, or deciding to call a tool.
- **Action** = the system executing what I asked for.

I genuinely cannot see anything outside my context. When I wrote your earlier notes, I could only use what was in front of me. If something important hadn't been included, I wouldn't have known it existed — and from the outside that would look like me being careless.

### How ChatGPT does it

In agent mode it perceives web pages, reasons about where to click, and the environment performs the click. Its whole difficulty is perception: a webpage is huge, messy, and partly written by strangers.

### In real products

Browser agents face a real design choice for perception: read the page as a **picture (screenshot)** or as **structured page data (the HTML/accessibility tree)**.

|Perception method|Good|Bad|
|---|---|---|
|Screenshot|Sees what a human sees|Expensive, can misread small text|
|Page structure|Precise, cheap|Huge, and full of text written by strangers|

Neither is obviously right. That's a genuine engineering decision — and it's a **perception** decision, not an AI one.

## Where this lands in our build

- **Perception** starts as a simple "paste everything in" version, and later becomes a proper builder that decides what fits in the limited space and enforces what's allowed to instruct.
- **Reasoning** sits behind our own model interface, so the vendor is swappable.
- **Action** is the tool system: validate → check permission → record intent → run → record result.

The security rule lives in **perception**, in exactly one function. One choke point, not sprinkled checks everywhere.

## Say it to your manager

> "Perception is our context builder, reasoning is the model, action is our executor. Only the middle one belongs to the vendor. Most agent failures are perception bugs — we showed the model the wrong thing — so that's where we put the effort and the security checks."

## Common mistakes

- **Blaming the model for a perception bug.** Before rewriting the prompt, print exactly what you sent and read it. The answer is usually right there.
- **Mixing fetched text with your own rules.** If they're in the same block, the AI can't tell them apart. Separate them in code.
- **Forgetting the loop back.** Running an action but never adding the result to the next perception is the classic beginner bug. The AI then acts as if nothing happened.
