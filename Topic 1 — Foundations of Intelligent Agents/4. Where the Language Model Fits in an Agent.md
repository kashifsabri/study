

Imagine a **brain in a jar**.

It's very smart. It can read and it can talk. But it has:

- no eyes
- no hands
- no notebook
- no clock

So you build a **robot body** around the jar:

- The body **shows** it things (reads files, opens websites).
- The brain **says** what to do next.
- The body **does** it.
- The body **shows** the brain what happened.
- Repeat.

**The AI model is only the brain. Everything else is the body — and you are building the body.**

---

## Simple technical version

The AI model does exactly one job:

> **Text goes in → text comes out.**

That's it. It can't run anything, save anything, or remember anything.

So an agent has to split the work:

|Job|Who does it|
|---|---|
|Gather the information and write it into text|**Your code**|
|Read that text and decide the next step|**The AI model**|
|Check that the decision is valid and allowed|**Your code**|
|Actually run the action (file, API, website)|**Your code**|
|Save what happened|**Your code**|
|Decide when to stop|**Your code**|

The AI does **one** of the six jobs. You do the other five.

### The shape of it

```
   your code builds the text (context)
              ↓
          AI MODEL          ← the only vendor part
              ↓
   your code reads the reply
              ↓
   is it an answer?  → STOP
   is it a tool request? → your code runs it
              ↓
   your code puts the result back in the text
              ↓
          (repeat)
```

## Code

### Step 1 — what the AI actually gives you

The AI replies with **text**. When it wants a tool, most providers return it in a structured shape like this:

```json
{
  "tool": "get_weather",
  "arguments": { "city": "Mumbai" }
}
```

That is **not** the weather. It's a **request** for the weather. Nothing has happened yet.

### Step 2 — the smallest possible agent loop

```python
def run_agent(user_question, tools, max_steps=5):
    # "context" = everything the AI is allowed to see
    context = [
        {"role": "system",  "content": "You are a helpful assistant."},
        {"role": "user",    "content": user_question},
    ]

    for step in range(max_steps):

        # 1. ASK THE AI  (the only place the model is used)
        reply = model.generate(context)

        # 2. IS IT A FINAL ANSWER?
        if reply.tool_call is None:
            return reply.text                    # done

        # 3. IT WANTS A TOOL — but WE decide whether to run it
        name = reply.tool_call.name
        args = reply.tool_call.arguments

        if name not in tools:
            result = {"error": f"no such tool: {name}"}
        else:
            result = tools[name](**args)          # WE run it, not the AI

        # 4. PUT THE RESULT BACK IN, AS INFORMATION ONLY
        context.append({"role": "assistant", "content": reply.raw})
        context.append({"role": "tool", "content": str(result)})

    return "Gave up: too many steps."
```

**Read the comments, not the code.** Four things to notice:

1. `model.generate(context)` is the **only** line where the AI is involved.
2. The AI returning `tool_call` is a **request**. The `if name not in tools` check is us refusing bad requests.
3. `tools[name](**args)` is **our** code running. The AI cannot reach this line.
4. `max_steps=5` is **our** stop button. Nothing in the AI would ever stop by itself.

### Step 3 — why we never call the vendor directly

Bad:

```python
# ❌ vendor locked into the loop forever
from groq import Groq
client = Groq()
reply = client.chat.completions.create(model="llama-3.3-70b", messages=context)
```

Good:

```python
# ✅ our own interface — the loop never knows who the vendor is
class ModelProvider:
    def generate(self, context): ...

class GroqProvider(ModelProvider):
    def generate(self, context):
        raw = self.client.chat.completions.create(...)
        return ModelResponse(
            text=...,
            tool_call=...,
            tokens_used=...,
            cost=...,
            latency_ms=...,
        )
```

**Why this matters:** the day you want to try a different provider, or fake the AI in a test, you swap one class. The loop doesn't change by a single line. This is a rule in our project, not a preference.

## Real-life examples

### How Claude does it

When I made your notes, I produced text that named a file-writing tool and its arguments. The system running me read that, created the file, and returned "file created." Then I decided to send it to you.

I never touched a file. I wrote text describing an action I wanted, and something else performed it.

### How ChatGPT does it

Same pattern, different name. With "function calling," the developer describes the available functions, the model outputs JSON naming one, and the developer's own code runs it and sends the result back.

### In real products

Every major provider's tool feature works this way: **the model names the tool, your code runs it.** If you've understood this one sentence, you've understood the core of every AI agent framework on the market.

---

## Where this lands in our build

Our `ModelProvider` interface is exactly the "Good" example above. It's one of the fixed rules of the project: **the loop never talks to a vendor SDK directly.**

Reasons:

- Swap Groq for anything else without touching the loop.
- In tests, replace the real model with recorded replies — no network, no cost.
- Cost, tokens and latency come back as proper fields, so we can measure spending.

---

## Say it to your manager

> "The model is one replaceable piece — the decision-maker. Everything that makes it safe, bounded and recoverable is our code. We wrap the vendor behind our own interface so the loop never depends on it."

---

## Common mistakes

- **Putting rules in the prompt that belong in code.** Writing "don't use more than 5 tools" in the prompt is a suggestion. A `max_steps` counter is a guarantee.
- **Calling the vendor SDK inside the loop.** It works on day one and hurts for the next year.
